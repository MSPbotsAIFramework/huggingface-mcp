## Product design

### Goals / Non-goals

**Goals (v1):**
- Expose Hugging Face Hub discovery as MCP tools: search and inspect models, datasets, and Spaces.
- Expose the authenticated user's identity and their own repos (models/datasets/spaces they own or belong to an org they are in).
- Expose a way to actually *run* something on Hugging Face — the ticket's "live access" language — via the Inference Providers chat-completion route, which is the broadest-coverage, lowest-risk way to let an agent get a model to do work without managing GPUs or hosting.
- Credentials are a Hugging Face user access token, supplied per request via a request header, never stored server side (this constraint was already written into the scaffold README by the prior DEV01 attempt; this design keeps it and makes it the header-auth contract).

**Non-goals (v1):**
- No repo creation, file/model upload, or any git/LFS-based write path — Hugging Face's write surface for repo content is fundamentally git-based (commits, LFS pointers for large binaries); that does not map onto a single stateless HTTP tool call and is excluded as a correctness/size risk, not merely deferred.
- No training/fine-tuning job management (AutoTrain) — no simple public API for it; most of that surface is UI- or partner-gated.
- No Spaces compute management (restart/pause/hardware changes) — operational/billing-adjacent, not "give an agent live access to Hugging Face content and inference".
- No webhook or OAuth-app management.
- No billing/usage/quota endpoints.

These non-goals mirror the Figma precedent (PRD-21325): a content-API vendor whose write surface doesn't map cleanly onto single-call MCP tools gets a read-plus-safe-action v1, with the gap recorded rather than silently implemented halfway.

### Acceptance criteria AC1..AC11

- **AC1** — Given a request with a valid `X-Huggingface-Token` header, when `huggingface_search_models` is called with a text query (and optional `task`/`library`/`author` filters), then the tool returns a list of matching models (`id`, `author`, `pipeline_tag`, `library_name`, `downloads`, `likes`, `tags`, `last_modified`), capped at `limit` (default 20, hard max 100), with `has_more` set when more results exist.
- **AC2** — Given a model `repo_id`, when `huggingface_get_model` is called, then it returns the model card metadata (tags, `pipeline_tag`, `library_name`, license, siblings count, gated flag) for an existing repo, or a `not_found` error for a repo that does not exist or is private and inaccessible with the given token.
- **AC3** — `huggingface_search_datasets` / `huggingface_get_dataset` behave symmetrically to AC1/AC2 for datasets.
- **AC4** — `huggingface_search_spaces` / `huggingface_get_space` behave symmetrically to AC1/AC2 for Spaces, and additionally surface the Space's `sdk` (gradio/streamlit/docker/static) and runtime `stage` (e.g. `RUNNING`, `BUILDING`, `SLEEPING`).
- **AC5** — Given a valid token, when `huggingface_whoami` is called, then it returns the authenticated identity (`name`, `fullname`, account `type` [user/org], and the list of organizations the user belongs to — names only, no billing/plan data).
- **AC6** — Given a valid token and an `owner` (defaults to the token's own identity), when `huggingface_list_owned_repos` is called with a `repo_type` (`model`/`dataset`/`space`), then it returns that owner's repos with `id`, `private`, `downloads`/`likes` where the Hub exposes them; an owner with zero repos returns an empty list, not `not_found`.
- **AC7** — Given a `repo_id`, `repo_type`, and optional `revision` (default the repo's default branch), when `huggingface_list_repo_files` is called, then it returns the file tree (`path`, `size`) for an existing revision, or `not_found` for an unknown repo or revision.
- **AC8** — Given a valid token, a `model` (provider-qualified, e.g. `meta-llama/Llama-3.1-8B-Instruct`), and a list of chat messages, when `huggingface_run_inference` is called, then it forwards an OpenAI-compatible chat-completion request to the Inference Providers router and returns the generated message text plus `finish_reason` and token usage if the provider reports it; upstream failures map to a structured error (`upstream_error` for 5xx/model-loading, `rate_limited` for 429 with `retryable: true`, `invalid_argument` for 4xx other than auth).
- **AC9** — Given a valid token and an existing model/dataset/space `repo_id`, when `huggingface_like_repo` is called, then the repo is liked for that user (idempotent — calling it again on an already-liked repo does not error and does not create a duplicate); calling it on a nonexistent `repo_id` returns `not_found`.
- **AC10** — Given any tool call missing the `X-Huggingface-Token` header, then the server returns HTTP 401 with a body naming the required header, before any outbound call to Hugging Face is attempted.
- **AC11** — Given two concurrent tool calls carrying two different tokens (tenant A and tenant B), then neither call's outbound request, response, or error ever uses or echoes back the other tenant's token or identity — verified at the contextvar/middleware layer, not just "the UI doesn't show it".

### Open questions

- **Q1 — exact set of inference tasks for v1 (not blocking).** Hugging Face's Inference Providers also cover non-chat tasks (text-classification, image-classification, embeddings, etc.) through task-specific routes, not only chat-completions. Assumption made: v1 ships chat/text-generation only (the OpenAI-compatible router), because it is the single task every provider in the router supports and it is the direct match for the ticket's "give Claude/ChatGPT/Cursor live access" framing (conversational delegation, not an embeddings pipeline). Additional task types are a natural, additive follow-up (new tool, no breaking change) if a concrete need shows up. Does not block v1.
- **Q2 — "every action logged" (not blocking).** The ticket's marketing copy promises action logging; this is already provided by the platform gateway's own audit logging for every tool call (same as every other connector), so no vendor-specific logging is added inside this MCP beyond the SOP's standard structured request logs (which never log the token itself). Flagging so a reviewer can object if "every action logged" was meant to imply something Hugging-Face-specific (e.g. mirroring into HF's own audit trail, which Hugging Face does not expose an API for). Does not block v1.

## Tech design

### Conclusion

Build a new Python/FastMCP MCP server in `MSPbotsAIFramework/huggingface-mcp` (currently an empty scaffold) implementing 11 tools against the public Hugging Face Hub REST API (search/get for models, datasets, Spaces; `whoami`; owned-repo listing; file-tree listing; like) plus one tool against the Inference Providers OpenAI-compatible router for chat/text generation, following `vendor-mcp-development` SOP v11 end to end (Streamable HTTP, stateless, header-only credentials, request-level isolation, structured errors).

### Where the current implementation lives

Nowhere — greenfield. `README.md:1-2` is the only content in the repo at `a84765f`.

### Option analysis

- **Language/runtime: Python 3.12 + uv + FastMCP** (SOP §9's recommended structure) vs. Node/TypeScript. Chosen Python: it's the SOP's primary path, and the comparable recent builds on this same queue for similarly-shaped "new read-heavy REST vendor" tickets (Box PRD-21298, Plaid PRD-21315, Figma PRD-21325, Keeper PRD-21235) all went this route, which keeps the fleet of MSPbotsAIFramework MCPs consistent for whoever maintains them next.
- **Credential transport: fixed-key header (`X-Huggingface-Token`) carrying a Hugging Face user access token** vs. OAuth. Hugging Face tokens are long-lived bearer strings (`hf_xxx`) scoped by the user at creation time (read/write/fine-grained) — they are exactly the "plain vendor" (fixed-key header) shape the SOP's `vendor-register` endpoint supports, confirmed against the platform's own precedent (`ProductDocs/_connector-fields.md` § Variant 1, ~45 existing connectors use one masked-token field). No OAuth app registration exists on Hugging Face's side for this use case, so OAuth was never a real option here, not just a path not chosen for convenience.
- **Inference target: Inference Providers router (`router.huggingface.co/v1/chat/completions`)** vs. the older single-backend Serverless Inference API (`api-inference.huggingface.co`). Chosen the router: it is Hugging Face's current, actively maintained multi-provider gateway and the one documented at `huggingface.co/docs/inference-providers` as of this writing; building against the serverless API would risk shipping against the deprecated path for many models. The router's request/response shape is OpenAI-compatible, which also keeps the tool's I/O schema simple and familiar for the calling agent.
- **One combined "search" tool per resource type with a `kind` parameter** vs. three separate `search_models`/`search_datasets`/`search_spaces` tools. Chosen three separate tools: each resource type's filter set differs enough (models take `library`/`pipeline_tag`; datasets take `benchmark`/`language`; Spaces take `sdk`) that a shared `kind` parameter would need a polymorphic filter object, which is harder for an agent to use correctly than three small, fully-typed tools. This keeps tool count at 11, still well under the SOP's 20-tool ceiling.

### Data & API contract

**Credential header** (declared in README, read in `middleware.py`):

| Header | Required | Meaning |
|---|---|---|
| `X-Huggingface-Token` | yes | Hugging Face user access token (`hf_xxx`), created at `https://huggingface.co/settings/tokens`. "Read" scope is sufficient for every tool except `huggingface_like_repo`, which needs "Write". |

**Tools** (11, all return a compact JSON string per SOP token-economy rules — no `indent=2`, `ensure_ascii=False`, list responses capped and truncated with `has_more`):

| Tool | Hints | Input (summary) | Output (summary) |
|---|---|---|---|
| `huggingface_search_models` | read-only | `query?`, `task?`, `library?`, `author?`, `limit?` (≤100, default 20) | `{items:[{id,author,pipeline_tag,library_name,downloads,likes,tags,last_modified}], has_more}` |
| `huggingface_get_model` | read-only | `repo_id`, `revision?` | model card fields, or `not_found` |
| `huggingface_search_datasets` | read-only | `query?`, `author?`, `limit?` | same shape as models, dataset fields |
| `huggingface_get_dataset` | read-only | `repo_id`, `revision?` | dataset card fields, or `not_found` |
| `huggingface_search_spaces` | read-only | `query?`, `sdk?`, `author?`, `limit?` | items incl. `sdk`, `stage` |
| `huggingface_get_space` | read-only | `repo_id` | Space metadata incl. `sdk`, `stage`, or `not_found` |
| `huggingface_whoami` | read-only | (none) | `{name, fullname, type, orgs:[name]}` |
| `huggingface_list_owned_repos` | read-only | `owner?` (default: self), `repo_type` (`model`\|`dataset`\|`space`), `limit?` | `{items:[{id,private,downloads?,likes?}], has_more}`, empty list if none |
| `huggingface_list_repo_files` | read-only | `repo_id`, `repo_type`, `revision?` | `{files:[{path,size}]}`, or `not_found` |
| `huggingface_like_repo` | idempotent, non-destructive write | `repo_id`, `repo_type` | `{liked: true}`, or `not_found` |
| `huggingface_run_inference` | non-idempotent (model calls can be non-deterministic), not destructive | `model`, `messages:[{role,content}]`, `max_tokens?`, `temperature?` | `{text, finish_reason, usage?}`, or structured error |

**Request example** (`huggingface_run_inference`):

```json
{"model": "meta-llama/Llama-3.1-8B-Instruct",
 "messages": [{"role": "user", "content": "Summarize: ..."}],
 "max_tokens": 256}
```

**Error envelope** (SOP §4, every tool, never a raw exception):

```json
{"error": {"code": "rate_limited", "message": "Hugging Face router returned 429", "retryable": true}}
```

**No DB, no migration** — this service holds no state of its own; every tool call is a pass-through to Hugging Face's own API.

### Key flow / sequence

```
Agent → Gateway (adds X-Huggingface-Token from the platform's stored, per-tenant credential)
      → huggingface-mcp /mcp (Streamable HTTP)
          → middleware reads header into contextvar, 401s if missing
          → tool handler → client.py → https://huggingface.co/api/* or https://router.huggingface.co/v1/*
          → errors.py maps non-2xx to the structured envelope
      ← JSON tool result (or structured error) ← Gateway ← Agent
```

### Non-functional

- **Idempotency/concurrency**: every tool is either naturally idempotent (reads; `like` is idempotent on Hugging Face's own side) or clearly marked non-idempotent (`run_inference`, since model output can vary); no tool retries a non-idempotent call automatically.
- **Performance**: `limit` capped at 100 (matches Hugging Face's own documented page-size ceiling); serialized tool output truncated at 20000 chars with `has_more`/`truncated` flag; one `httpx.AsyncClient` per request, not a long-lived pool holding one tenant's auth state.
- **Security**: token read only from the declared header, never logged, never written to disk, never cached across requests; outbound calls only ever go to `huggingface.co` and `router.huggingface.co`; `gitleaks detect` run before delivery; no other vendor or company name appears in the repo besides MSPbots and Hugging Face.
- **Multi-tenant isolation (AC11)**: `contextvars.ContextVar` set in middleware and `reset()` in a `finally`; no module-level or class-level variable ever holds a token; `tests/test_middleware.py` exercises two concurrent requests with different tokens and asserts neither client observes the other's identity.
- **Logging/observability**: structured request logs (tool name, status, latency, no header values); `/health` returns `{"status":"ok"}` independent of Hugging Face's own availability (SOP §1.1 — a Hugging Face outage must not make this service's own health check fail).

### Rollout & rollback

This is vendor registration, not an update to an existing vendor: the first version is merged to `main`, then registered via `/api/vendor-register` with `credential_fields = {"X-Huggingface-Token": {"label": "Access Token", "type": "password", "required": true, "description": "Hugging Face user access token (Settings → Access Tokens)", "example": "hf_xxx"}}`. Rollback is trivial because there are zero existing tenants on this connector before this ticket: if the first INT deploy fails health checks, nothing is registered and nothing breaks for anyone. Future changes (new tools, parameter changes) go through the ordinary `/api/deploy-int` path per the SOP's change-management rules (§13): breaking changes (renamed/removed tools or params) require advance notice; additive changes (new optional params, new tools) ship normally.

### Test strategy

- **Automated** (`tests/test_tools.py`, `tests/test_middleware.py`): `tools/list` snapshot (11 tools); per-tool happy path and the SOP error-code mapping (401/403/404/422/429/5xx) against a mocked `httpx` transport — no real Hugging Face account needed for any of this; the 401-without-header and concurrent-token-isolation cases (AC10, AC11) are fully internal and automated too.
- **Manual, needs a real Hugging Face account** (listed in the report as "needs a real vendor account" per the SOP — not a blocker for shipping): `whoami`, `list_owned_repos`, `run_inference` end to end against a live provider, and `like_repo` end to end (liking requires a Write-scope token against a real account). - **Local, no account needed**: `initialize → tools/list` with a placeholder Bearer-shaped token (format only, not a real credential), confirming tool count/shapes and the 401 path.
- **Regression surface**: none yet — greenfield repo, nothing to regress against.

### Decisions made by DEV01

No product decision-maker is reachable in this unattended design pass, and the ticket itself names no concrete capability (it is Conduit marketing boilerplate). These are the choices made to ship a coherent, bounded v1, each with the alternative that was not taken:

1. **Scope = Hub discovery (models/datasets/Spaces search+get) + identity + owned-repo listing + file listing + one idempotent write (`like`) + chat-style inference.** Why: this is the largest useful slice of "give an agent live access to Hugging Face" that stays entirely within single-call, stateless HTTP semantics. Alternative not chosen: also covering repo creation/file upload — rejected because Hugging Face's write path for repo content is git/LFS-based and does not fit a single MCP tool call without reimplementing a git client inside the service.
2. **Credential header name `X-Huggingface-Token`.** Why: matches the SOP's `X-<Vendor>-<Credential>` convention and Hugging Face's own terminology ("access token"/"user access token"). Alternative not chosen: `X-Huggingface-Api-Key` — rejected because Hugging Face's own docs and UI never call it an "API key", and matching the vendor's own vocabulary reduces confusion for whoever fills in the credential later.
3. **Inference limited to the OpenAI-compatible chat-completions route for v1 (Q1).** Why: broadest provider coverage, simplest/most-familiar schema for an agent to call. Alternative not chosen: also wiring task-specific routes (text-classification, embeddings, etc.) in v1 — deferred as a low-risk additive follow-up rather than guessing at which non-chat task is actually wanted.
4. **Default list `limit` 20, hard cap 100.** Why: mirrors Hugging Face's own documented API default/maximum page size, keeping tool responses small without inventing a different ceiling.
5. **`huggingface_like_repo` is the only "write" tool in v1.** Why: it is low-risk, naturally idempotent, and demonstrates the write path exists without any destructive or bulk-write surface (matches the non-goals: no create/delete/upload).

- **TC-HGF-005** (AC2, exception) — Given a `repo_id` that does not exist, when `huggingface_get_model` is called, then it returns `not_found`, not a raw 404 passthrough or a 500.
- **TC-HGF-006** (AC3) — Given `query="imdb"`, when `huggingface_search_datasets` is called, then matching datasets are returned with the documented fields.
- **TC-HGF-007** (AC3, exception) — Given a nonexistent dataset `repo_id`, when `huggingface_get_dataset` is called, then it returns `not_found`.
- **TC-HGF-008** (AC4) — Given `query="gradio"`, when `huggingface_search_spaces` is called, then matching Spaces are returned including `sdk` and `stage`.
- **TC-HGF-009** (AC4, exception) — Given a nonexistent Space `repo_id`, when `huggingface_get_space` is called, then it returns `not_found`.
- **TC-HGF-010** (AC5, needs a real vendor account) — Given a valid token, when `huggingface_whoami` is called, then it returns the token owner's `name`/`type`/`orgs`.
- **TC-HGF-011** (AC5, exception, needs a real vendor account) — Given a syntactically-present but invalid/expired token, when `huggingface_whoami` is called, then it returns `unauthorized` (mapped from the Hub's 401), not a raw exception or 500.
- **TC-HGF-012** (AC6, needs a real vendor account) — Given a token for an account with zero repos of a given `repo_type`, when `huggingface_list_owned_repos` is called, then it returns an empty `items` list, not `not_found`.
- **TC-HGF-013** (AC7) — Given an existing public `repo_id` and its default revision, when `huggingface_list_repo_files` is called, then it returns the file tree with `path`/`size` for each entry.
- **TC-HGF-014** (AC7, exception) — Given an existing `repo_id` but a nonexistent `revision`, when `huggingface_list_repo_files` is called, then it returns `not_found`.
- **TC-HGF-015** (AC8, needs a real vendor account) — Given a valid token, a provider-served `model`, and a one-turn `messages` list, when `huggingface_run_inference` is called, then it returns generated `text` and a `finish_reason`.
- **TC-HGF-016** (AC8, exception, needs a real vendor account) — Given a `model` that is currently loading/unavailable on every provider, when `huggingface_run_inference` is called, then it returns `upstream_error` with `retryable: true`, not a raw 503.
- **TC-HGF-017** (AC8, exception, needs a real vendor account) — Given a provider that returns 429, when `huggingface_run_inference` is called, then it returns `rate_limited` with `retryable: true`.
- **TC-HGF-018** (AC9, needs a real vendor account) — Given a valid Write-scope token and an existing, not-yet-liked repo, when `huggingface_like_repo` is called twice in a row, then both calls succeed and the second call does not error or create a duplicate like.
- **TC-HGF-019** (AC9, exception, needs a real vendor account) — Given a nonexistent `repo_id`, when `huggingface_like_repo` is called, then it returns `not_found`.
- **TC-HGF-020** (AC10, exception/security) — Given a tool call with no `X-Huggingface-Token` header, when any tool is called, then the server returns 401 naming the required header, before any outbound Hugging Face call is made (verified via the mocked transport receiving zero calls).
- **TC-HGF-021** (AC11, exception/security, OWASP API Top 10 — broken object-level authorization adjacency) — Given two concurrent requests carrying token A and token B respectively, when both call `huggingface_whoami` at the same time, then request A's response never contains token B's identity (or vice versa), verified at the contextvar/middleware layer with a mocked Hub client.
- **TC-HGF-022** (performance, needs a running instance) — Given the service running locally with a mocked Hugging Face backend, when 10 concurrent `huggingface_search_models` calls are sustained for 30 seconds, then the P95 latency added by the MCP layer itself (excluding the mocked backend's simulated latency) is ≤ 500ms, and no response contains another concurrent request's data.
